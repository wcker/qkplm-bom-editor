# ADR-0001：唯一规范源与三层交付架构

- 状态：已接受
- 日期：2026-07-18
- 规范依据：[v2 白皮书](../../现代化高性能可复用BOM编辑器组件.md)，重点参见第 0、2、16、17 章

## 上下文

仓库存在不同阶段形成的产品设想和落地文档，其中对渲染方式、Worker 使用、撤销容量、智能修复和性能口径可能存在不同描述。如果多份文档同时被当作规范，实现、测试和验收会各自选择不同口径，无法形成稳定的公开契约。

产品同时需要服务 Vue 3、React 和原生 HTML。若各框架分别实现模型、事务或性能逻辑，会产生行为漂移、重复缺陷和无法比较的性能结果。另一方面，把所有 Core 代码都视为任意运行时可执行，也会使 headless、浏览器、Worker 和文件模块发生环境依赖污染。

## 决策

1. 根目录 `现代化高性能可复用BOM编辑器组件.md` 的 v2 白皮书是 `@bom-editor/*` 的唯一规范源。其他白皮书、产品说明、示例和 ADR 均不得与其竞争规范地位。
2. 采用稳定的三层交付架构：
   - Core 内核层：领域模型、索引、事务、Diff、调度、渲染、Worker 协议、插件协议和可选文件能力。
   - 框架适配层：Vue 3、React、UMD/原生 JS 的薄适配，只负责挂载、生命周期桥接、事件转发和参数透传。
   - Demo 与验收层：固定数据、功能演示、基准、兼容性验证和机器可读报告。
3. Core 继续按运行时边界拆分公开子路径。`contracts`、`model` 和 `transaction` 不访问 DOM；Canvas、DOM 编辑、快捷键等只进入 browser 边界；Worker 和文件模块通过版本化协议接入。
4. 依赖必须单向流动。适配层和 Demo 只能依赖 Core 的公开出口，不得读取 `internal` 状态，也不得实现索引、事务、业务规则或改变 Core 语义。
5. ADR 用于解释和固化决策，不直接凌驾于白皮书。规范变更必须先更新白皮书，再以新 ADR 替代旧决策。

## 后果

### 正面后果

- 产品、实现、测试和发布门禁共享同一验收口径。
- 三种宿主接入共享同一正确性和性能内核，减少行为差异。
- headless、浏览器、Worker 和文件能力可以独立打包、测试、按需加载并遵守 CSP/SSR 约束。
- 架构例外有可追溯的评审记录和回退路径。

### 代价与约束

- 白皮书变更需要同步审查公开类型、测试、Demo 和 ADR，治理成本高于随意修改实现。
- Core 需要维护清晰的子路径、条件导出和协议版本，构建矩阵更复杂。
- 框架特有体验只能通过公开扩展点实现，适配层不能通过复制内核逻辑快速绕过限制。

## 被否决方案

### 多份白皮书并列作为规范

否决原因：冲突时没有确定的优先级，无法建立自动化门禁和兼容承诺。

### Vue、React 和原生版本各自实现编辑器内核

否决原因：算法、事务和事件时序必然漂移，性能优化与缺陷修复需要重复投入。

### 单一不可拆分的 Core 入口

否决原因：会迫使 headless/SSR 使用方引入 DOM 类型和浏览器副作用，也妨碍 Worker、XLSX 与渲染能力按需加载。

### 以 ADR 直接覆盖白皮书条款

否决原因：会再次形成隐蔽的多规范源问题，且调用方无法从正式规范判断真实行为。

## 验证方式

- CI 检查所有正式需求、公开 API 和验收用例都能追溯到 v2 白皮书条款。
- 使用 DOM、WebWorker 和 Node/SSR 三组 TypeScript `lib` 配置编译对应公开子路径。
- 通过依赖图或 lint 规则阻止适配层实现内核模块、阻止 headless 模块导入 browser 模块、阻止外部读取 `internal`。
- 对 Vue 3、React StrictMode、Vue KeepAlive、UMD 重复挂载运行同一组适配器契约测试。
- 生产构建验证 XLSX、Worker 和 browser-only 能力不会进入不使用它们的入口，并记录各入口包体积。
