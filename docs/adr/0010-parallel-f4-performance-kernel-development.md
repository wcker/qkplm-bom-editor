# ADR-0010：F3 证据未闭合期间并行推进 F4 性能内核

- 状态：已接受
- 日期：2026-08-06
- 规范依据：[v2 白皮书](../../现代化高性能可复用BOM编辑器组件.md)，重点参见第 1.2–1.4、6、7、8、14、15 章

## 上下文

F3 的 10K 可编辑纵向链路、自动回归和正式浏览器证据 runner 已完成候选实现，但当前正式报告仍因 compositor trace 数据完整性、Realm 噪声资格和人工可访问性/soak 证据未闭合而不能准出。与此同时，用户明确将工作重点转向 100K 性能内核，要求直接进入 F4。

白皮书原有阶段顺序把 F3 作为 F4 的入口依赖。直接把 F3 标记为通过会伪造发布证据；继续冻结 F4 则无法建立 100K 性能基线、识别投影和渲染路径的实际瓶颈，也不符合当前优先级。

## 决策

1. 从 2026-08-06 起，F4 以并行研发模式激活。该模式只授权 100K fixture、投影/索引、Canvas 虚拟化、调度、Worker 派生任务、搜索索引及其测试和基准建设。
2. F3 保持未准出：`releaseQualified`、`f3Pass` 与任何 GA/发布结论继续为 `false`。F4 的开发、基准和内部 API 不得被表述为 F3 通过、F4 通过或可发布版本。
3. F4 的首项交付是可重复的 100K 基线：`BOM-100K-D6` 与 `BOM-100K-FLAT` 必须覆盖全部折叠、部分展开和全部展开，并分别记录构建、投影、查询、展开/折叠、滚动窗口和内存结果。
4. 性能优化不得降低 Snapshot 不变量、事务原子性、取消/代际检查、Policy、安全限额、ARIA/DOM 语义或 F3 证据 runner 的 fail-closed 行为。任何公开 API 或协议变化仍需独立 ADR、API 报告和迁移审查。
5. F3 证据修复仍作为并行阻断项保留；通过 F4 基准不能替代 compositor trace、正式 Realm、人工 WCAG/读屏或 soak 证据。

## 后果

### 正面后果

- 100K 的真实数据结构和浏览器瓶颈可以提前量化，不必等待与功能内核无关的 F3 证据环境问题。
- 每项 F4 优化有固定 fixture 和可比较原始样本，避免凭局部微基准改变公开行为。
- F3 的发布证据边界保持诚实，后续可以独立恢复和重跑 formal。

### 代价与约束

- 需要同时维护 F3 回归和 F4 基准，任何共享模块改动都扩大验证面。
- F4 结果在 F3 未闭合时只能作为研发证据，不能用于发布宣传或阶段准出。
- 大对象和 Worker 优化必须有主线程回退、取消和资源所有权测试，不能只追求吞吐量。

## 被否决方案

### 将 F3 直接标记为通过

否决原因：当前 report 已明确拒绝资格化；修改结论而不消除 trace/Realm/人工证据缺口会破坏白皮书的发布门禁。

### 继续冻结 F4 直到 F3 全部证据闭合

否决原因：用户已改变研发优先级，且 100K 基线、投影和渲染内核可以在不改变 F3 资格结论的前提下独立研发。

### 只运行一次本机 100K 脚本

否决原因：单次结果不具可比性，也无法覆盖树形/扁平、展开状态、滚动窗口和内存边界。

## 验证方式

- 为两个 100K fixture 建立版本化 headless 与浏览器场景，归档未舍入样本、环境、构建和 fixture 哈希。
- 对投影和索引建立 100K 正确性测试，覆盖深树、扁平树、全折叠、部分展开、全展开、随机查询、行高变化及展开/折叠后的双向索引一致性。
- 每项 F4 变更运行受影响的单元/属性测试、`pnpm typecheck` 和相关基准；公开入口变化继续通过 API Extractor。
- F3 runner 继续保持 fail-closed，独立报告不得被 F4 结果覆盖或改写。
